# Million Items Manager

Два списка над 1 000 000 элементов с общим серверным состоянием в памяти: выбор, сортировка Drag & Drop, фильтрация, пагинация по 20, батчинг и дедупликация запросов.

- Source: https://github.com/NikolayYaroslavcev/million-items-manager
- Live demo: _появится после деплоя на Fly.io_

## Запуск

Нужны Node.js ≥ 22.12 (см. `.nvmrc`) и pnpm 11 (`corepack enable`).

```bash
pnpm i
pnpm dev                 # сервер :3000 (tsx watch) + Vite :5173 с прокси /api → http://127.0.0.1:3000
pnpm check               # lint + format + typecheck + unit/integration-тесты (shared, server, web)
pnpm test:large          # серверные тесты на миллионном наборе (T15)
pnpm test:e2e            # сборка + Playwright против production-сервера (T19–T21, T29–T32, DnD, ошибки)
pnpm test:perf           # сборка + замеры производительности → apps/web/perf-results.json
pnpm build && pnpm start # production: один процесс отдаёт API и SPA на :3000
pnpm smoke http://localhost:3000   # production smoke (добавьте --long для 5-минутной проверки SSE)
pnpm build && pnpm --filter @mim/server load --duration 60 --connections 200   # нагрузочный тест T23
pnpm --filter @mim/server bench:rekey             # перегенерация ключей порядка на 1 млн
docker build -t mim . && docker run -p 8080:8080 mim   # затем http://localhost:8080
```

Перед первым `pnpm test:e2e` установите браузер: `pnpm --filter @mim/web exec playwright install chromium`.

Конфигурация — переменные окружения, см. [.env.example](.env.example); `DEBUG_ENDPOINTS` и `SEED_SELECTED` — только для замеров: с `NODE_ENV=production` сервер с ними не стартует (нагрузочный тест и `test:perf` запускают ту же сборку с `NODE_ENV=test`).

## Структура

```
packages/shared   общие zod-схемы, коды ошибок, типы ответов и событий, константы, позиция курсора
apps/web
  src/sync        клиентское ядро без React: ListMirror (окно + журнал), движок синхронизации,
                  слой ожидающих операций, SSE поверх fetch, резервный опрос, лидер вкладок
  src/api         HTTP-клиент: таймауты, повторы с тем же Idempotency-Key, классификация исходов
  src/ui          React: виртуализированные списки, DnD (dnd-kit), клавиатура, добавление ID
  test/, e2e/     unit и property-тесты (T8, T27), транспорт (T29–T31); Playwright e2e и замеры
apps/server
  src/store       чистые структуры данных: битовая карта + B+-дерево ключей порядка, nextMatch, инварианты
  src/core        engine (тики, фазы, очереди, стадии prepare/commit/respond), идемпотентность, SSE, курсоры
  src/http        Express: маршруты, валидация, rate limit, обработка ошибок
  src/runtime.ts  сборка сервисов и жизненный цикл (graceful shutdown, аварийный режим)
  test/           unit, property, integration, fault-injection; test/large — миллионный набор
```

## Проверенные гарантии

- **Атомарность (I10):** мутация применяется через журнал отмены; при сбое — откат и сверка со снимком (500 `INTERNAL`, доказано «не применено»), иначе 500 `OUTCOME_UNKNOWN` и аварийный перезапуск. Проверено внедрением сбоя после каждой записи каждого типа мутации (T25a–c).
- **Однократность:** с `Idempotency-Key` операция не применяется дважды ни при каком исходе (T2, T9–T11, T24, T25b, T25d).
- **Линеаризуемость батча:** ADD → мутации (FIFO) → публикация → чтения; каждая страница — срез одной версии (G1).
- **Полный журнал:** каждое изменение получает версию; SSE-реплей по `Last-Event-ID` и `/api/changes` отдают одинаковые данные (T18, smoke).
- **Event loop:** бюджет сканирования 100 000 и 250 мс на чтения за тик; p99 задержки 23 мс при тяжёлых фильтрах по 1 млн выбранных (T15).
- **Перезапуск сервера:** каждый ответ и событие несут `instance` (UUID процесса); версии разных экземпляров никогда не сравниваются, поэтому клиент не примет новую историю за продолжение старой, даже если её версия больше (T32).
- **Ключи порядка:** нехватка места для ключа решается локальной перегенерацией окрестности (≤ 1,6 мс на 1 млн выбранных, обычные записи `moved` в журнале, без смены эпохи); глобальная O(n) (~0,67 с) — только запасной путь.
- **Нагрузка (T23):** 60 с × 200 соединений, смешанные чтения и мутации, в том числе на 1 млн выбранных: 0 ошибок 5xx, p95 чтений ≈ 1,05 с (тик 1 с), инварианты и реплика журнала сходятся с сервером.

## Ограничения

Состояние живёт в памяти одного процесса: перезапуск его сбрасывает (клиенты это обнаруживают по `instance` и перезагружают данные), масштабирование — только одна реплика (fly.toml). Каждый запрос отвечается на ближайшем секундном тике (по ТЗ), поэтому пропускная способность ограничена ≈ числом соединений в секунду. Поиск редкой подстроки по 1 млн выбранных занимает ≈ 10 с (10 запросов по 100 000 кандидатов, каждый на своём тике) — ограничение бюджета сканирования; в интерфейсе виден прогресс.

## Деплой на Fly.io

`fly.toml`: одна машина без автоостановки (состояние в памяти), `kill_timeout` 10 с > `SHUTDOWN_TIMEOUT_MS` 8 с, health-check `/api/health`, HTTPS принудительно, 512 МБ ОЗУ при куче 384 МБ.

```bash
fly auth login
fly launch --copy-config --no-deploy   # один раз: создать приложение из fly.toml
fly deploy
fly scale count 1
pnpm smoke https://<app>.fly.dev --long  # API, SSE 5 мин без событий, HTTP/2, заголовки безопасности
```
